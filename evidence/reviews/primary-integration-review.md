1. **P1: An empty tab can invalidate another tab's runtime.** `packages/web/src/App.tsx:44` guards update activation using only this page's busy flag and inputs. `scripts/service-worker.ts:13` generates activation that deletes every previous app cache and calls `clients.claim()`. With two app tabs, applying an update from the empty tab replaces the controller and removes cached old assets under the tab holding images. Cancellation terminates that tab's worker, and `packages/web/src/client.ts:8` recreates it using the old build's worker URL. If deployment removed that URL, retry fails instead of retaining a usable offline runtime. Reproduce with build A in a tab containing images, deploy B, open a second empty tab and apply its update, then cancel and retry in the first tab. This is a source-confirmed protocol gap; that exact two-tab browser reproduction is NOT RUN. Guard activation across app clients or preserve assets while old clients need them, then test the transition. T02/T03/T16 remain incomplete.

2. **P2: Failed attempts have no dependable recipe identity.** At `packages/web/src/App.tsx:123`, the manifest takes `recipe_hash` exclusively from a retained successful result. `process` at lines 73–80 does not store an attempted hash. A first-run failed or unscheduled item omits it; a failed rerun with an older result reports the old output's recipe hash for the new failure. This violates §07's per-item resolved recipe identity and makes changed-recipe failure/resume evidence ambiguous. Record the planned/attempted recipe and binding identity separately from any retained output identity. Verify a corrupt first run and a failed rerun after changing the recipe. Monotonic input references, indexed filenames, typed failures, and preservation of invalid/completed statuses are otherwise coherent by inspection.

3. **P2: A CLI test depends on an expiring production observation.** `tests/cli-boundary.test.ts:138` requires the Japan pin to return `notices: []`. The catalog intentionally expires observations after 24 hours. In a separate Node process, replacing only `Date.now` with `2026-10-10T04:08:01.782Z` and resolving that same pin produced `unknown` freshness and a `source-freshness` notice, while preserving its ID/version. The test will then fail despite correct production behavior. Keep the CLI pin/JSON checks independent of wall-clock freshness; retain the dedicated catalog tests covering fresh, expired, failed, and changed sources.

`docs/catalog-freshness.md:13` also claims the workflow is manual-only and has no schedule, contradicting the restored daily cron in `.github/workflows/catalog-sources.yml:3`.
